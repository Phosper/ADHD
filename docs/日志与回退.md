# 日志与回退协议

分为开发对话记录、运行会话记录和发布版本记录。三者相互关联，但不能互相代替。当前开发记录与 Git 检查点已建立；运行采集器、重放、备份工具尚待实现。

## 1 每次开发对话

每次对话一个独立 Markdown 文件，命名含上海时间、主题和唯一后缀，避免多人争抢同一个日志文件。使用 `docs/devlogs/TEMPLATE.md`，起始记录写明 HEAD 和已有未提交改动，结束时补齐实际变更、检查和下一步。

记录用户需求和已确认决策的摘要，不保存逐字全文或内部推理。历史补录标注“事后摘要”，不得伪造当时检查点。需要完整聊天原文时由团队另行保留平台导出；AGENTS.md 只能约束读取并遵循它的协作者，不能自动截获所有人的聊天工具。

每个有变化的对话建立一个或多个范围明确的本地提交。提交说明包含开发日志路径。日志中的结果提交可写“包含本日志的提交”，通过 `git log --all -- <日志路径>` 找到，避免把提交自身哈希写入自身导致循环变更。CI/PR 结果可在后续独立补录中关联原提交。

只讨论的对话也建立日志；代码回退时保留日志，追加回退记录说明原因及验证结果。不要修改旧日志来隐藏失败。

## 2 每通业务对话

建议事件字段：schema_version、event_id、event_type、session_id、trace_id、span_id、producer_id、producer_seq、session_seq、turn_id、generation_id、timestamp_utc、observed_at_utc、monotonic_ns、severity、payload、release_id。

服务端记录 UTC 时间，界面按 Asia/Shanghai 展示。单调时钟只用于同进程耗时；跨设备时钟不能直接相减。浏览器事件单独保留采集时间和服务端接收时间，报告时注明校准方法。结构参考 [OpenTelemetry 日志数据模型](https://opentelemetry.io/docs/specs/otel/logs/data-model/)，项目字段是我们的扩展，不声称已实现 OTel 全协议。

必须区分以下事件：

- `session.started/ended/aborted`：建立、正常结束、异常终止。
- `speech.started/ended`、`asr.partial/final`：活动检测与转写，partial 不作为已确认槽位。
- `response.proposed/validated/cancelled`、`playback.started/stopped`：生成、校验和用户实际听到的内容。
- `state.changed`：旧状态版本、新状态版本、触发事件及规则版本。
- `tool.requested/committed/failed/unknown/reconciled`：工具提案、实际副作用和状态查询，不能合并成一个 success 字段。
- `quality.completed`、`logging.degraded`：质检与日志不完整信息。

业务状态与审计事件在同一数据库事务内持久化；外部调用用持久化待办记录请求、幂等键和回执，重启先对账。事件使用 event_id 去重，中心写入方分配 session_seq；客户端重传不造成重复业务操作。

关键审计持久化失败时暂停新的业务写入，允许播放安全结束提示；不能静默继续操作并宣称日志完整。partial 等高频诊断事件可按明确策略采样，但关键状态、最终转写、播放确认、工具副作用和结束事件不采样。

启动时扫描未结束会话，标记中断、对账工具状态并补生成可用质检报告。报告注明日志缺口，不能自动判通过。

原始录音、转写和完整模型输入保存在受控运行目录，Git 中仅保留合成样例、Schema 和摘要。日志最小化，屏蔽凭据和敏感字段；权限与保留期须由团队依据赛题要求设定，现场测评数据按要求销毁。哈希可校验内容一致性，但没有签名和权限控制时不能声称防篡改。

## 3 每次发布与每通会话绑定 manifest

manifest 至少包含：release_id、代码 commit、工作树是否干净、依赖锁哈希、镜像 digest、各模型 ID/revision/权重哈希、提示词哈希、业务规则与知识库哈希、非敏感配置哈希、数据库 schema_version、测试集版本和测试报告引用。

正式版本要求工作树干净；开发运行标记 dirty 并保存受控补丁引用，不能与发布基线混报。记录随机种子、采样配置和推理参数，仍不保证 GPU/LLM 完全逐字确定。

## 4 四种恢复方式

**代码与配置回退：**在干净独立分支中对目标变更生成 revert，评审后合入；不强推共享历史。如果提交含开发日志，撤销实现时保留旧日志并增加新记录，再提交撤销结果。先检查后续提交是否依赖它，不能只看一条提交的名称。

**模型与知识回退：**部署上一份完整 manifest 指定的模型、提示词和知识快照，而不是只把 Git 代码切旧。旧资产保留到验证期结束，恢复前检查哈希和数据库兼容性。

**数据库恢复：**先停止新写入并使用一致性备份；SQLite WAL 模式不能运行中只复制主 db 文件。用数据库备份接口制作快照，在隔离目录验证恢复、行数和版本，然后才切换。恢复可能丢掉备份之后的结果，须通过事件和工具回执对账，不自动执行破坏性恢复。

**外部业务副作用：**代码回退不会撤销已登记工单。为可撤销动作定义显式补偿请求及独立幂等键；不可撤销动作转人工。重放旧日志默认不调用真实写接口。

## 5 回放与重新运行

只读回放：按 session_seq 展示当时事件和已保存的输出，不重新推理或调用工具。

隔离重演：复制合成/获准快照到独立 Mock 环境，以固定版本运行模型，产生新的 session_id 并关联 original_session_id，用于比较；不得覆盖原始证据。模型重跑可能不同，应报告差异而不是声称恢复了原会话。

需要验证：工具提交后进程崩溃、回执丢失、重复事件、日志磁盘不可写、打断后迟到音频、版本缺失、恢复后幂等、重放零真实副作用。
