# 基线项目文件规划

状态：目录说明和协作文件已落地，下面列出的代码文件均为待建。以已确认的基线设计 v0.4 为业务依据；本文件细化工程划分，不宣称已经实现基线。

## 1 采用单仓库与明确模块边界

使用一个仓库统一版本，前端 TypeScript，后端 Python。业务核心、契约、持久化与实时语音分开，ASR/LLM/TTS 分进程隔离依赖。先以 Mock 让无 GPU 的成员完成业务和前端工作，再与校园网 A100 联调。

不按每个组件创建一个独立仓库，也不在第一阶段加入复杂消息平台。目录划分对应团队负责范围；接口和验收标准先确定，再允许并行实现。

## 3 依赖方向和数据所有权

`apps/web → contracts → services/api / services/voice → domain 的抽象接口`。`storage`、`knowledge`、模型适配器实现这些接口。`domain` 不导入 Pipecat、FastAPI、数据库驱动或厂商模型 SDK。

- API 层是业务状态、单据版本、工具写入和会话事件序号的唯一权威写入方。
- Voice 层拥有瞬态音频管线与取消状态，通过协议请求业务状态变化，不直接修改业务数据库。
- 浏览器只报告采集、播放和用户操作，不自行认定身份通过、任务完成或工具成功。
- 模型只提供意图、槽位和动作提案；服务端检查后执行。
- 运行事件先可靠持久化，JSONL 是可重建的导出视图，避免多个进程并发向同一文件追加。

边界发生变化时先修改 ADR 和契约，防止团队各自理解一套字段。

## 4 首批共享契约

先定义：创建/结束/查询会话、提交用户最终转写、提案校验、工具执行及回读、事件查询、质检查询。官方 Mock 尚未提供，标明自建接口与官方适配的区别。

所有请求带 request_id；会话关联 session_id/trace_id；写入带 idempotency_key 与 expected_version；错误统一为 code、可读说明、retryable、operation_id。超时允许“状态未知”，不得直接按失败重复创建副作用。

实时事件至少包含用户语音开始/结束、ASR final、回复代号变更、客户端播放开始/停止、状态变更、工具状态与会话结束。契约必须规定顺序、重复、丢失及重连后的处理，前后端不能只对齐 JSON 字段名。

## 5 双模式开发

Mock 模式：合成单据、模拟语音事件、固定的模型适配响应、真实状态机和 SQLite 事务。用于多人独立开发，不依赖校园网，不冒充真实模型测试。

A100 模式：替换 ASR/LLM/TTS 适配器，其余业务与结果契约保持一致。先单会话真实语音，记录网络和显卡共享情况，再做目标测试。

不做基于测试用例 ID 的答案特判。Mock 的固定响应只存在测试环境，运行界面和报告必须标记模式。

## 6 先后关系

第一批建契约、日志基础、数据导入与状态机；随后业务/前端/模型模块可按已定契约并行。文本闭环和可靠回写通过后再接真实语音，最后冻结评测和比赛部署。

每个任务需要可检查的完成条件，详见任务看板。目录 README 当前仅用于明确所有权和接口，不作为功能验收证据。
