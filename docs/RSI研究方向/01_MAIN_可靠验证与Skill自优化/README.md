# 主线 可靠验证驱动的 Skill 自优化

**研究目标：在相同计算预算下，更可靠地选出能改善业务处理能力的提示词或 Skill。** 这是智语外呼项目的优先候选方向，尚未在本项目上验证有效。

## 1 用一个例子说明

需要防范这样一种评测失真：AI 客服要求商家补齐材料，新话术更容易引出“知道了”，裁判便给出“任务完成”的高分；但商家从未明确答应整改。即使程序守卫阻止了错误回写，这个分数也不能证明沟通能力提高。

因此，自动改进不仅要会提出新话术，还要能判断：这次修改减少了真实错误，还是只让系统更容易拿高分。这里的 Skill 是程序实际使用的任务处理说明或策略，例如在什么条件下澄清、先解释什么、何时转人工。

## 2 为什么以这三项工作为基础

| 工作与来源 | 已经做了什么 | 对本项目的作用 |
| --- | --- | --- |
| **GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning**：[论文](https://arxiv.org/abs/2507.19457) · [代码](https://github.com/gepa-ai/gepa) | 阅读执行轨迹，分析失败，提出并测试提示词修改 | 先建立一套可比较的优化基线 |
| **RRSI: Regularized Recursive Self-Improvement of Agent Harnesses**，v3：[论文](https://arxiv.org/abs/2609.24972v3) · [代码](https://github.com/google-research/rrsi) | 约束修改过程，检查针对评测的过拟合，处理分数波动、成本和无效组件 | 参考如何接受、拒绝和停用改动 |
| **EvoSkill v2: Fully Agentic Skill Evolution from Benchmark Adaptation to a Stateful Evolver**：[论文](https://arxiv.org/abs/2610.25931v2) · [代码](https://github.com/sentient-agi/EvoSkill/tree/v2) | 演化器保留跨轮状态，读取多次训练轨迹并修改技能；每轮采用新技能，避免按噪声分数反复挑选 | 比较另一种处理波动和技能更新的方式 |

这些工作说明，自我反思、评分阈值、多次尝试和历史记录都已有研究。我们的潜在贡献应进一步收窄，而不是把这些机制换个场景就称为创新。

## 3 建议研究的具体问题

**能否根据一次改动声称解决的问题，自动选择最有诊断价值的测试，并用有限预算判断它是否值得保留？**

例如候选声称修复了“含糊确认被误判”，可以检查三类案例：

- **表达变化，真实意愿不变。** “知道了”与“明白你的意思了”都不能自动视为愿意整改。
- **表达接近，真实意愿变化。** “我会补齐”与“我还不能答应补齐”需要不同处理。
- **表达相同，对话条件变化。** “是”回答身份问题与回答整改确认问题，含义不同。

验证器从候选改动和训练失败中选择这些案例，决定哪些需要追加测试，最后接受或拒绝候选。待检验的增量是测试选择和预算分配是否改善最终版本，而不是配对案例本身。是否具有新颖性，还需继续与主动测试和序贯评价等工作比较。

## 4 怎样接入现有 ADHD 基线

当前 Qwen3-8B 主要输出十类意图，业务状态机决定回复和回写，尚无自动加载 Skill 的执行器。因此分两步接入。

**第一步只优化分类提示词。** 将 `ModelClient.interpret` 使用的固定提示词改为可显式传入的候选文本，保持输出格式、业务守卫、状态机和模型一致。GEPA 适配器负责运行候选，收集分类和业务结果，再把训练失败转换成反思材料。原始模型输出、守卫修正后的结果、最终业务状态要分别记录。

**第二步再开放受控沟通策略。** 如果要学习如何解释或追问，需要一个新接口：模型根据当前阶段、已确认事实和已审核知识提出沟通动作，程序验证后才采用。初期可以只允许选择有限模板；身份事实、业务规则和写入条件仍由统一业务层维护。此时才能评价完整沟通 Skill 的收益。

源码定位：[当前模型入口](https://github.com/Phosper/ADHD/blob/41afa0c67904de9ef07a5d1445dbcfb86e1e7565/services/api/model_client.py)、[当前状态机](https://github.com/Phosper/ADHD/blob/41afa0c67904de9ef07a5d1445dbcfb86e1e7565/packages/domain/state_machine.py)、[GEPA 适配器接口](https://github.com/gepa-ai/gepa/blob/cb7674c8b231270134b8e5ea8b9db1a62ed8d081/src/gepa/core/adapter.py)。这些链接用于进一步定位，接入逻辑已在上文说明。

RRSI 的完整实现会生成和评估候选代码工作树，初期只借鉴其选择机制更容易控制范围。EvoSkill v2 原实现依赖 Claude Code 技能执行与容器环境，不能只替换模型地址就接入 Qwen。若移植时改变执行器、修改空间或更新规则，实验中应明确说明与原方法的差异。

## 5 怎样证明改进来自我们研究的机制

需要区分两种比较。

| 比较 | 固定什么 | 改变什么 | 回答什么 |
| --- | --- | --- | --- |
| 优化流程整体比较 | 模型、业务边界、任务、总预算 | 原始版本、人工修订、GEPA，后续增加其他优化流程 | 哪套流程在本项目更有效 |
| 验证方法比较 | 同一批候选、评分标准和总预算 | 固定测试、随机追加测试、诊断性测试选择 | 收益是否来自测试选择方法 |

最终报告独立测试中的业务正确率、错误回写、严重错误、正确转人工，以及提案、模拟、评分和复测的总成本。一次测试没有发现错误不等于零风险，需要多次运行并报告按案件统计的波动范围。

训练案例用于提出修改，开发案例用于选择配置，封存测试只用于最终报告。同一案件的改写和语音变体必须放在同组。若根据封存测试继续修改，这些案例就已成为开发材料，需要新的最终测试。

EvoSkill v2 的“每轮采用新技能”可以在隔离实验中作为对照；实际部署仍要经过共同发布门禁。若在实验中也额外拒绝其更新，就必须标明算法已经变化。

## 6 阶段交付和停止条件

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| 接入验证 | 候选执行接口、逐轮记录、原始版本对照 | 候选确实进入模型请求；原始版本行为可复现；不同试验互不污染 |
| 基础比较 | 原始版本、人工修订和 GEPA 的同预算报告 | 改进出现在独立案例中，而不只出现在已有开发题上 |
| 方法研究 | 测试选择机制及拆除关键机制的对照 | 同预算下最终版本更好、无效改动的误接受更少 |
| 语音复核 | 最终候选的语音、打断与时延报告 | 文本收益能保留到实际语音链路中 |

若只有开发分数提升、业务错误增加，或收益主要来自模拟器漏洞，应暂停扩展并修正评价。当前基线尚有 B0 验收待办，实施顺序遵循项目任务看板。具体负责人和教师调用预算由团队确认。
