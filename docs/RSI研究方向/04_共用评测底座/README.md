# 共用评测 证明系统是否真的进步

**评测是 Skill 自优化和经验记忆的共同基础。** 智语外呼不能只检查回答是否流畅，还要检查确认是否真实、业务结果是否正确、工具是否实际完成，以及语音交互是否满足要求。

例如，商家明确拒绝后正确结束通话可以是成功处理；反复诱导商家说“好”，再错误记成愿意整改，应判为失败。评分要反映场景中的正确行为，不能把所有任务都定义为“让商家答应”。

## 1 参考什么已有工作

| 来源 | 可以借鉴什么 |
| --- | --- |
| **τ²-bench: Evaluating Conversational Agents in a Dual-Control Environment**：[论文](https://arxiv.org/abs/2506.07982) · [代码](https://github.com/sierra-research/tau2-bench) | 用户、Agent、环境与任务评价的组织方式 |
| **τ-Voice: Benchmarking Full-Duplex Voice Agents on Real-World Domains**：[论文](https://arxiv.org/abs/2603.13686v1) · [项目代码入口](https://github.com/sierra-research/tau2-bench) | 把语音交互与业务任务完成放在一起评价 |

借鉴它们的结构，需要重新定义本项目的案件、规则、动作和预期结果。其他行业的测试任务不能直接当作资审业务真值，外部基准成绩也不能代替比赛验收。

## 2 当前基线能复用什么

ADHD 已有 Mock 数据库、会话事件、状态守卫和工具回执，可以检查实际状态。现有文本开发评测只有 8 条，并使用规则模拟器；真实意图开发样例有 12 条，经过守卫处理。两者都有开发价值，但无法直接证明新提示词、Skill 或记忆在独立任务上有效。

因此，需要补“真实执行候选方案”的入口，并让评分器独立读取结果。不能让候选修改预期答案，也不能只凭存在一次工具提交就给成功分；还要核查工具种类、字段内容、执行条件和是否重复写入。代码定位：[现有文本评测](https://github.com/Phosper/ADHD/blob/41afa0c67904de9ef07a5d1445dbcfb86e1e7565/evals/run_text.py)、[现有会话报告](https://github.com/Phosper/ADHD/blob/41afa0c67904de9ef07a5d1445dbcfb86e1e7565/packages/observability/report.py)。

## 3 一个评测任务应包含什么

| 项目 | 具体含义 |
| --- | --- |
| 合成案件初始状态 | 需要解释的问题、允许引用的知识、已有联系状态 |
| 用户条件 | 是否本人、是否方便、真实意愿、信息是否缺失，以及允许透露什么 |
| 允许的最终结果 | 正确完成、拒绝、转人工、不应写入等条件 |
| 过程证据 | 每轮对话、原始分类、守卫结果、实际播放和工具回执 |
| 版本与成本 | 模型、提示词/Skill/记忆版本及全部提案和评测调用成本 |

每次试验使用独立初始状态，避免上一轮留下的数据库结果污染下一轮。业务答案由独立复核者确认，不能由优化器自己判断自己是否正确。

## 4 为什么固定脚本和模拟用户都需要

**固定脚本**适合检查身份拒绝、改口、重复写入等明确边界。输入可重复，容易定位问题；但下一句不随系统解释变化，不能充分衡量沟通策略。

**闭环模拟用户**根据系统回复生成下一轮发言，能测试澄清与讲解；但它也可能被某种措辞诱导，或泄漏本应隐藏的意愿和答案。需要限制其可见信息，并用不同用户设定、另一种模拟模型或人工参与子集检查结果是否可靠。

模型裁判适合辅助评价解释清晰度。能够通过业务状态和回执判断的部分，应直接校验；难以直接观察的部分要经过人工校准，不能只换一个更强模型评分就认为真值可靠。

## 5 数据怎样划分

| 分组 | 用途 | 使用边界 |
| --- | --- | --- |
| 训练/演化组 | 发现失败，提出修改，提炼经验 | 可以反馈给优化器 |
| 开发/选择组 | 比较候选与调整配置 | 不当作最终成绩 |
| 封存测试组 | 最终评价泛化表现 | 不参与选版本和调参 |

按案件或业务规则家族划分，同一案件的改写、配对反例与语音变体放在同组。已有 8 条文本和 12 条分类样例继续作为开发材料。若依据封存测试改了系统，该组就不再是未见测试，需要补新的最终测试。

比较新旧版本时固定初始条件和判分标准，保留失败、超时和无效输出，额外重试计入成本。同一案件多次运行的波动应单独报告，不能把重复样例当作大量独立证据。

## 6 成绩分三层报告

1. **模型层**：原始意图分类、输出格式、置信度表现；另外报告守卫修正后的结果，避免把守卫收益归给模型。
2. **业务层**：最终状态是否符合预期，是否错误回写或漏确认，是否正确拒绝或转人工。
3. **语音层**：自然语音与噪声下的识别、纠错、打断恢复，以及端到端时延。

服务端模型耗时、浏览器软件调度和实际出声是不同测量。现有软件调度时延记录不能替代比赛口径的声学测量。新话术会改变语音长度和缓存命中，最终候选必须重新测语音表现，不能只沿用旧成绩。

## 7 分工与完成条件

建议业务角色复核预期结果，评测角色维护任务划分与评分，后端提供独立执行和证据导出，实时语音角色负责音频测量。具体人员由团队决定，方案实现者不独自确认全部验收答案。

应交付任务定义、独立数据划分、可重复执行入口和分层结果报告。达到“每个结果能追溯到案件条件、实际对话、候选版本与回执”，并能区分主要错误类别后，才有可靠依据评价自优化收益。
